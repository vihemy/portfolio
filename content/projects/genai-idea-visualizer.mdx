The *Dødvande* ("Dead Water") exhibition at **Kattegatcentret**, the Danish aquarium in Grenaa, is anchored by an installation that turns visitor ideas into generated images. Guests walk up to a fantastical sci-fi–themed enclosure, type an idea for improving the ocean environment into a text-input screen, and watch as the machine "transforms" their idea into an imaginative illustration — synchronized across four displays and a DMX light fixture.

## Challenge

The brief was simultaneously simple and demanding: a visitor types a sentence, the installation produces a beautiful AI-generated image of their idea, and the whole thing has to feel like one coherent machine — input, processing, output, sound, and lighting all in lockstep — running unattended for the length of an exhibition.

Three constraints shaped the design:

1. **The audience is the general public, including children.** The input is free text — the installation has to moderate before it sends anything to a commercial image API.
2. **The output has to make sense for the exhibition.** "Idea Machine" is part of *Dødvande*; an AI-generated portrait of a random unrelated concept would dilute the show. The installation has to classify whether a submission is *on-topic* before promoting it into the rolling slideshow.
3. **It runs alone, for months, in a gallery.** Whatever breaks — the internet, the API, a sensor, the lights — has to fail *gracefully*, and what the gallery staff can fix without me should be fixable without a rebuild.

## Approach

I modelled the whole installation as a **finite state machine** — `Idle → Input → Processing → Output` — driven by a `GameManager`, with each collaborator (audio, lighting, dashboards, network, slideshow) wired to the FSM transitions rather than to each other. Adding or removing a piece of the show changes one wiring, not a graph of them.

### Two model calls, not one

A single image-generation request would have made the architecture simpler and the result worse. The pipeline makes **two** OpenAI calls:

1. A **DALL·E** image-generation call against the visitor's (moderated) prompt.
2. A **completion/chat** call that evaluates the prompt against the exhibition's relevance topics — *ocean*, *pollution*, *farming*, *inventions*, and so on — and stores an `isRelevant` flag in the metadata.

The 15 most-recent "relevant" images loop in the on-screen slideshow; *irrelevant* but still-generated images are archived locally and never promoted. If nothing relevant has been submitted yet, fallback entries from `StreamingAssets/FallbackEntries/` keep the slideshow populated — so *Dødvande* never opens to a blank wall.

### Profanity filtering in three languages

The museum's audience is Danish, English-speaking, and German-speaking. The profanity filter loads three word lists — `profanity_da.txt`, `profanity_en.txt`, `profanity_de.txt` — from `StreamingAssets`, and a rejected prompt returns a graceful "couldn't use that one" path through the FSM rather than failing the submission visibly.

### Configurable without a rebuild

Everything an operator or I might want to tune lives as plain text in `StreamingAssets/config.txt`:

- `API_KEY`, `API_IMAGE_URL`, `DALLE_MODEL`, `DALLE_N`, `DALLE_SIZE`
- `API_CHAT_URL`, `GPT_MODEL`
- `SYSTEM_CONTEXT` — the relevance criteria; the topics are editable, with two trailing sentences locked to keep the contract with the classifier

(editing the profanity lists is the same kind of edit). Reconfiguring the show at the venue does not involve Unity, and does not involve me flying to Grenaa.

### Four displays and one DMX fixture, in lockstep

A `DashboardManager` animates the "transformation" effect across two dedicated dashboard screens while the input and visualization screens carry their part of the show. `LightController` renders sprite-based light effects and flash routines on beat with the dashboard, and coordinates with the **DMX fixture** at show time. An `AudioManager` + `AudioTriggerer` pair handles crossfades and triggered cues. Every one of those is wired to FSM events, never ad-hoc.

### Persistence and recovery

Generated images are downloaded via `UnityWebRequest`, saved as JPG alongside a JSON metadata file (prompt, name, age, creation time, relevance flags) in `Application.persistentDataPath`. The slideshow reads from there on boot, so an exhibit that woke up offline still has something to show from yesterday's relevant submissions.

## Outcomes

Visitors approach a sci-fi machine, type an idea, watch it transform, and walk away telling the next person in the queue what *they* would have typed instead. The show has the integrity the curators wanted — the slideshow only displays submissions that are both clean and on-topic — and the staff can keep it running without me, because every dial is a text file. The full FSM, profanity filter, OpenAI integration, image downloader, dashboard, audio, and light controller are visible at `github.com/vihemy/dinide`; that's the work.
